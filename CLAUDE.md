## Database — Prisma ORM 8 + Supabase

Connection strings live in `.env` (gitignored): `DATABASE_URL` = Supabase transaction-mode pooler (port 6543, `?pgbouncer=true`) for the runtime client; `DIRECT_URL` = session-mode pooler (port 5432) for CLI-side operations, wired through `prisma.config.ts`. The Supabase project is live and the password in `.env` is filled in — the CLI and the app both reach the real database.

Prisma 8 rearchitected the CLI: there is no `prisma validate` / `prisma generate`. The contract source is the Prisma-7-style `prisma/schema.prisma`, consumed via `prisma7Schema()` in `prisma.config.ts`; `npx prisma contract emit` compiles it to `src/prisma/contract.json` + `contract.d.ts` (both committed). The runtime client is `src/prisma/db.ts` — import `db` from there, do not instantiate your own client. Supabase agent skills are installed under `.claude/skills/` and pinned in `skills-lock.json`.

**Models** (migrations in `migrations/app/`, committed):

- *Search* — `SearchLog` (append-only: `service`, `href`, `values` jsonb, `createdAt`).
- *Catalog* — `ServiceLine` → `ServiceType`, `Product`, `ProductPackage`, `PriceTier`, `Amenity` / `ProductAmenity`, `ProductAddOn`. `Airport` is the shared place reference (kind `airport` | `city`, `iataCode` unique when set). Product JSON columns (`included`, `notIncluded`, `requirements`) are string arrays. Dynamic-option fields are the ⚙ ones the BookingBox renders as select fields — their option lists come from `getOptions(kind)` actions: `Airport` (for `airport`/`city`), `ServiceType`, `Airline`, `Country`.

### Place hierarchy (parent → child)

Places form a **data-driven hierarchy**: every place may point at a parent place through `Airport.parentId` (self relation `PlaceHierarchy`, `ON DELETE SET NULL` / `ON UPDATE CASCADE`) and carries a `sortOrder` inside its group. The tree is generic — a city parents the airports below it, but any place may parent any other — and nothing is hardcoded.

- `src/lib/places.ts` — pure helpers on plain rows: `placeLabel()`, `buildPlaceTree()` (missing parents become roots, cycle-safe), `filterPlaceTree()` (keep the ancestors of the requested kind), `flattenPlaceTree()` (rows + depth for the admin table), `descendantPlaceIds()` (cycle guard), `placeMatches()` / `hasPlaceMatch()` (query filtering).
- `getPlaceOptions(kind: "airport" | "city")` (`src/app/actions/catalog.ts`) returns the pruned `PlaceNode[]` tree — parents as group headers, leaves as the selectable options. The submitted value stays the leaf label (`"Soekarno-Hatta (CGK)"`), so the existing search/filtering is unaffected.
- `src/components/ui/PlaceOptionList.tsx` renders the grouped list (indented children, non-selectable parent headers, query-aware).
- The admin Places screen (`src/app/admin/(secure)/catalog/places/PlacesManager.tsx`) manages the hierarchy: a *Parent* select (excluding the place itself and its own descendants) and an *Urutan* (sort order) field; the table is rendered as an indented tree. `upsertAirport()` rejects self-parenting and cycles server-side.
- *Booking* — `Booking` (header; `code` unique `BV-…`, `status` ∈ `awaiting_payment`|`confirmed`|`cancelled`|`completed`, `serviceAt`, pax counts, integer USD-cent totals, unique `invoiceNumber` (`#INV/YYYY/MM/DD/NNNN/XX`)), `BookingItem` (per package line), `BookingAddOn`, `Contact` (1:1), `Traveler*`, `FlightDetails` (1:1), `Payment*`, `PaymentMethod`.
- *Accounts* — `User` (id = the Firebase UID, `email` unique, `name`, `phone`, `role` ∈ `ADMIN`|`USER` (default `USER`), `emailVerified`, timestamps). `Booking.userId` points at it (nullable — guest bookings stay `null`, FK `ON DELETE SET NULL` / `ON UPDATE CASCADE`). The **role column is the source of truth** for the admin/user split.
- *Payments* — `PaymentMethod` (code/label + gateway binding: `provider` `"xendit"` | null, `providerMethodCode` `"CREDIT_CARD"`), `Payment` (the USD base `amountUsdCents` plus the frozen IDR charge snapshot — `providerAmountCents` (whole rupiah × 100), `providerCurrency` `"IDR"`, `fxRate`, `providerRef` (the Xendit `ps-…` session id), `reference` (our invoice number, `-R<n>` suffix on retry), `checkoutUrl`, `expiresAt`, `rawPayload`), `PaymentWebhookEvent` (the webhook dedupe/audit ledger, unique per `provider` + `providerEventId`). See **Payments** under Architecture. The old `Currency` / `ExchangeRate` tables are gone — there is no display-currency system anymore.

All money values are **integer USD cents** on the wire and in the DB, and **every customer-facing price is displayed in USD** — there is no currency switching and no client-side FX. Booking totals are immutable once created — they record the quote the customer saw. The only USD→IDR conversion in the app is the server-side charge rate applied when a payment session is created (see Payments). Schema history: migration `20261117T0745_usd_only_xendit` dropped the `Currency`/`ExchangeRate` tables and the Booking/Payment FX columns and normalized legacy DOKU amounts; `20261117T0850_payment_idr_charge` added `Payment.providerCurrency` + `fxRate` for the IDR charge snapshot. The DOKU gateway is fully removed.

The Prisma 8 loop for a schema change is:

```bash
npx prisma contract emit          # schema → contract.json + contract.d.ts
npx prisma migration plan --name <slug>   # write the migration package (offline)
npx prisma db migrate             # apply it to the live database
npx prisma db sign                # record that the DB matches the contract
```

**App usage:** queries go through `db.orm.public.<Model>` (e.g. `db.orm.public.SearchLog.create({...})`, `.select(...).orderBy(...).limit(n).all()`; filtered writes like `.where(...).deleteAll()`). Server Actions in `src/app/actions/search.ts` (`logSearch`, `getRecentSearches`) wrap the DB for the UI and swallow errors, so the UI keeps working from the localStorage copy when the database is unreachable. `logSearch` dedupes identical submissions (same service + href + values refreshes `createdAt` instead of inserting) and prunes rows older than 30 days (`RETENTION_DAYS`) on every insert. Never read the database during render of a statically prerendered page — the pages stay static and fetch from the client.

## Architecture

Marketing + booking concierge site (Booking VIP, a tiket.com-style educational clone). Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4. Supabase Postgres via Prisma 8 (see Database). Firebase Authentication for the admin area and for customer accounts. Server Actions own all DB writes; the UI falls back to static/`localStorage` data when the database is unreachable so browsing never breaks.

**Composition:** `src/app/page.tsx` (server component) assembles the whole home page. `StickyAppBanner` is intentionally left commented out in `page.tsx` — don't "fix" that by re-enabling it unless asked.

**Routes:**

- `/` home, `/search?q=…` search results, `/my-booking` lookup by code+email.
- `/login`, `/register` — the customer sign-in / sign-up area (see "Customer accounts" below). `/account` — the signed-in customer's profile + their bookings.
- Four service-line indexes — `/vip-service`, `/transport`, `/tour-package`, `/evoa` — each fed by `getCatalog(lineSlug)` (DB-first, falls back to static `src/data/home.ts` content on error). Each line also has a `/<line>/[slug]` product detail page fed by `getProduct(slug)`.
- `/airport-vip` is the **airport VIP booking tool** — the site's single service (fast track + document handling for foreign tourists; Transport/Tour/eVOA are hidden from nav/home but their routes still work). A 7-step wizard (country → airport → schedule → flight → service → passengers → confirm) rendered by `AirportVipWizard`, fed by the readers in `src/lib/airport-vip.ts`, prefilled from the hero search query params (`nationality`, `airport`, `date`, `dateTime`, `paxAdults`/`paxChildren`). Copy is i18n (`wizard.*` keys, EN primary). The **country step is the traveller's own country of origin** (`Country` table, with `voaEligible` flag) — it tells the traveller whether we handle a Visa on Arrival; it is stored in `Contact.nationality`. The catalog is **one product per airport** (`airport-vip-<iata>`, seeded by `npm run db:seed-airport-vip`) with package tiers (Fast Track / VIP + Lounge) plus the `voa-handling` add-on; legacy VIP products are deactivated. The passenger step collects **per-traveler passport data + photo**: name, passport number, nationality, DOB, expiry (validated ≥ 6 months after service) and a photo uploaded via `/api/uploads/passport` to the **private** R2 bucket (`putPrivateObject`; only the key is stored in `Traveler.passportPhotoKey`, admin previews use `signedDocumentUrl`). `createBooking` writes the passport fields, sets `Traveler.docStatus` (`received` when number+photo present), and creates a linked `VisaApplication` when the VOA add-on is booked. The four side panels (service description, add-ons, base price, booking rules) come from `Setting` keys `vip.serviceInfo` and `booking.rules` plus the product's own fields; the surcharges in the rules table are **display only** — nothing applies them to a total.
- **VIP operations & tracking** — `/admin/orders` (actions in `src/app/actions/admin-orders.ts`, gated like the rest of admin) is the back office: order list, per-traveler document verification (`docStatus`), the ops workflow (`Booking.opsStatus`: `waiting_documents → processing → ready → in_service → done`), greeter assignment (`greeterName`/`greeterPhone`) and VOA status. Customers track the same state via the `VipTracking` component (`src/components/booking/VipTracking.tsx`): shown under `/my-booking` lookups and on `/account/orders/[code]` (session-owned lookup `getMyOrderTracking` in `src/app/actions/order-tracking.ts`, which delegates to `getBookingByCode` after proving ownership).
- `/booking/[slug]` is the 4-step wizard (`BookingWizard` → contact → travelers → flight → payment) driven by `createBooking`. On success it creates the booking and redirects straight to the Xendit hosted checkout — there is no result step; `/payment/return` takes over after the charge. On failure it surfaces the server error inline.
- `/payment/return?code=…` — where Xendit redirects back after checkout; polls the payment status until it is paid or failed (see Payments).

**Server Actions** (`src/app/actions/`):

- `search.ts` — `logSearch`, `getRecentSearches` (see Search flow).
- `catalog.ts` — `getCatalog(lineSlug)`, `getProduct(slug)`, `getOptions(kind)` (airports/cities/serviceTypes/airlines/countries), `getPlaceOptions(kind)` (the grouped place hierarchy), `getPaymentMethods()`. All return `null`/`[]` on error so the client can fall back.
- `booking.ts` — `createBooking(input)` (validates product/package/lead-time, re-computes totals server-side from DB cents, generates unique `BV-…` code, sequential inserts with compensating deletes on failure), `getBookingByCode(code, email)` (discriminated result). Also seeds the provider-less placeholder `Payment` row the gateway later fills.
- `payments.ts` — `startBookingPayment`, `getBookingPaymentStatus`: thin wrappers over `src/lib/payments.ts` so the browser never talks to the gateway directly (see Payments).
- `admin.ts` — the admin area's data + mutation layer (see "Admin area" below). Also holds the reserved webadmin API (`upsertServiceType`, `upsertAirport`, `upsertPriceTier`, `upsertProduct`, `upsertPackage`, `upsertPaymentMethod`, `upsertAirline`, `upsertCountry`). **Every exported function throws unless `process.env.ADMIN_ENABLED === "1"` *and* the caller holds a valid admin session.** Validates integer USD-cent prices ≥ 0, slug/code uniqueness before write, `unitKind` consistency (`per_pax` → adult/child/infant; `per_unit` → unitUsdCents; duration → hours+extraHour), boolean active flags. `upsertAirport` also takes the hierarchy fields (`parentId`, `sortOrder`) and rejects self-parenting and cycles.
- `admin-crud.ts` — the admin **create / update / delete** layer used by the catalog form pages and the delete modal: `saveAdminEntity({ table, id, values })`, `deleteAdminEntity({ table, id, confirmName })` and `getAdminEntityName()`. Both write actions return a **structured result** (`{ ok, message }` / `{ ok: false, error, field? }`) instead of throwing, so a field-level validation error survives the server-action boundary. `deleteAdminEntity` compares the typed name with the stored name character for character (no trimming, no case folding) and refuses to delete a record that other rows still depend on.
- `admin-auth.ts` — admin sign-in / sign-out (`signInAdmin`, `signOutAdmin`).
- `user-auth.ts` — customer sign-in / sign-up / sign-out (`signInUser`, `registerUser`, `signInUserWithGoogle`, `requestPasswordReset`, `signOutUser`, `getSessionUser`).

**Navigation:** `src/components/layout/NavBar.tsx` is the primary navbar — a working search form (submits to `/search?q=…`, index built in `src/data/search.ts`), the four service links (`serviceNav`) with `usePathname()` active state, and a mobile drawer behind a hamburger button. It is rendered inside `Header`, which is a client component with two variants: `overlay` (transparent over the home hero, becomes fixed + white after 80px of scroll) and `solid` (sticky white bar, used on the sub-pages). Both variants keep the navbar on every page.

**Search flow:** the home hero form (`HeroSearch`) selects a service with the category rail and fills real inputs; pressing **Search** navigates to that service page with the entered values in the query string (`/transport?pickup=…&pax=…&service=Transport`). Field keys per service live in `serviceSearchFields` (`src/data/services.ts`) and the field *kind* decides how the field renders: `select-airport` / `select-city` / `select-service-type` / `select-country` open a searchable dropdown (the airport and city dropdowns render the **grouped place hierarchy** — see "Place hierarchy" above), `datetime` renders a trigger that opens a date + time panel (the hour is stored in the sibling key `<key>Time`), `pax` renders the passenger counter (counts in `<key>Adults` / `<key>Children` / `<key>Infants`, plus a readable summary in `<key>`). The shared widgets are `src/components/ui/Popover.tsx` (a trigger + floating panel that closes on outside click or Escape and starts with a headless-UI style *focus guard*), `src/components/ui/DateTimePopover.tsx`, `src/components/ui/PaxPopover.tsx` and `src/components/ui/FieldShell.tsx`. The submitted search is stored twice: in the database (Server Action `logSearch` → `SearchLog` table, cross-device) and on the device (`src/lib/searchDraft.ts` localStorage — last search + five recent). The home form pre-fills from the local copy, the "Pencarian terakhir" section (`RecentSearches`) reads the database with a localStorage fallback, and the sub-page falls back to the local copy when the URL carries no values.

**Locale + currency:** `src/components/providers/LocaleProvider.tsx` is mounted in the root layout and exposes `useLocale()` — `{ lang, setLang, formatMoney, t }`. That shape is a hard contract; the old `currency` / `setCurrency` / `rates` fields were removed with the IDR display-currency system — **there is no currency switching and no client-side FX anymore**. Language (`en` | `id`) persists in `localStorage` (`booking-vip:locale`); on mount the provider also deletes the stale `booking-vip:fx` / `booking-vip:currency` keys left by older builds. `formatMoney(usdDollars)` is pure USD formatting via `formatMoneyWith` in `src/lib/currency.ts` (`Intl.NumberFormat` en-US USD; the module exports only `CurrencyCode = "USD"` and `formatMoneyWith`) — pass dollars (`cents / 100`), never cents. Components rendered inside the home page's streamed Suspense boundary use the hydration-safe `useMountedLocale()` (`src/lib/useMountedLocale.ts`) instead of `useLocale()` directly: it renders EN defaults on the first commit (matching the server HTML) and flips to the stored locale before paint. Translations live in `src/i18n/{en,id}.ts`; components take the dict key as a prop (the `"use client"` component calls `t("key")` from `useLocale()`), **not a translated string** — the key-as-prop rule keeps the component tree locale-agnostic and lets server-rendered copy flow through the same dictionary.

**Payments — Xendit (display USD, charge IDR):** the gateway is **Xendit Payments API v3**, **Credit Card only**, via Payment Sessions (`src/lib/xendit.ts`, server-only; the former DOKU integration is fully removed). `startPayment` (`src/lib/payments.ts`) POSTs `https://api.xendit.co/sessions` with `session_type: "PAY"`, `mode: "PAYMENT_LINK"`, `currency: "IDR"`, `country: "ID"`, `allowed_payment_channels: ["CARDS"]`, `allow_save_payment_method: "DISABLED"`, then redirects the customer to the returned `payment_link_url` — Xendit's hosted checkout, where the card form and 3DS live. **No card data ever touches our server.**

- **Currency model** — display is USD everywhere; the *charge* is IDR. At session creation `src/lib/payments.ts` converts `booking.totalUsdCents` to whole rupiah with `getUsdToIdrRate()` + `convertUsdCentsToIdr()` from `src/lib/fx.ts` (server-only): the public **Frankfurter API** (`https://api.frankfurter.dev/v1/latest?base=USD&symbols=IDR`, 5 s timeout) with a hard-coded fallback rate of **16500**, rounded to the nearest rupiah (minimum 1). This is the only FX conversion in the app — server-side plumbing, never a display rate.
- **Frozen snapshot** — the `Payment` row records `amountUsdCents` (the USD base), `providerAmountCents` (rupiah × 100), `providerCurrency` `"IDR"`, `fxRate` (the rate used), `providerRef` (the `ps-…` session id), `reference` (our invoice number `#INV/YYYY/MM/DD/NNNN/XX`, with a `-R<n>` retry suffix, capped at 64 chars), `checkoutUrl`, `expiresAt` (~24 h; the response's `expires_at` is authoritative) and `rawPayload`. `createBooking` seeds a provider-less placeholder `Payment`; the first successful session fills it, a retry after a failed/expired attempt gets a fresh row, and an unexpired pending session is re-used instead of creating a second one. The amount is always the server-computed booking total, never one from the browser.
- **Webhook** — `POST /api/payments/webhook/xendit` verifies the `x-callback-token` header against `XENDIT_WEBHOOK_VERIFICATION_TOKEN` (timing-safe; a bad token gets a 401 and changes nothing). It handles `payment_session.completed` / `.expired` and `payment.capture` / `.authorization` / `.failure`, and tolerates legacy `credit_card.authentication` / `.capture` / `.tokenization` dashboard test deliveries (`data.id` / `data.external_id`) — those are informational and can never confirm a booking. The dedupe key is `event:objectId:status`, stored in `PaymentWebhookEvent` (unique per provider), so a replayed delivery is a no-op. A paid event only confirms when the amount (× 100) matches `providerAmountCents`; confirmation is idempotent → `Booking` `"confirmed"` + a loyalty-points recompute (`recomputeUserPoints` re-derives the balance from source rows, so webhook + return page double-calling is harmless).
- **Return page** — `/payment/return?code=…` (`PaymentReturn`) polls `getBookingPaymentStatus` every 5 s while the payment is pending; the service refreshes the session via `GET /sessions/{id}` and applies the same amount-match rule, so the page self-heals when the webhook is late. Ownership is proven by booking code + contact email (the email is recovered from `booking-vip:last-booking` in localStorage, or asked for).
- **Env & dashboard** — `XENDIT_API_KEY` (secret, HTTP Basic auth), `XENDIT_WEBHOOK_VERIFICATION_TOKEN`, and `XENDIT_PUBLIC_KEY` (reserved for a future client-side Components integration, currently unused). Return URLs **must be HTTPS** — local development needs an HTTPS tunnel (e.g. ngrok) set as `NEXT_PUBLIC_APP_URL`. In the Xendit dashboard: point the webhook URL at the deployment and allowlist the server's egress IP.
- **Verification** — `scripts/tmp/verify-xendit-webhook.mts` exercises the whole path against a live session: session creation → completion webhook → paid/confirmed → dedupe → amount-mismatch rejection → bad-token 401 → cleanup.

**Transport stock (rental cars):** `Product.stockTotal` is how many units of the vehicle the vendor owns. Available stock is **derived, never stored** — `src/lib/stock.ts` computes `getAvailableStock(productIds)` as `stockTotal − reserved`, clamped at 0. Reservations come from `BookingItem.vehicleCount` (one line per booked car): `confirmed` bookings always reserve their lines; `awaiting_payment` bookings reserve for **24 h** after creation (`STOCK_RESERVATION_TTL_MS`) and then **lazily expire** — no cron, an old unpaid row simply stops counting; `completed` / `cancelled` reserve nothing, so a handover or cancellation releases the units with no stock write. `assertStockAvailable` is the write-side guard used by `createBooking`. The transport listings (`getCatalog`) **hide zero-available cars** from every listing including the home carousel; other service lines are unaffected.

**Cart bookings (transport):** `createBooking` accepts an `items[]` array — several rental lines in ONE booking with **one invoice and one payment**. Each line carries `productSlug`, `packageId` (must be an active `per_day` transport package), `days` (1–365, default 1) and `vehicleCount` (1–99, default 1); the line price is `unit × days × vehicleCount`. Stock is checked per product over the **sum** of that product's cart lines before anything is written. Each line becomes one `BookingItem` (`quantity` = rental days, `vehicleCount` = the units the line reserves; the header `Booking.vehicleCount` is the cart total). `Booking.idempotencyKey` (unique) makes a double-submitted checkout safe: the client generates one UUID **per attempt** (`useState(() => crypto.randomUUID())`, rotated for a fresh attempt) and an insert race returns the earlier booking instead of creating a duplicate.

**Admin area (`/admin`):** a guarded, white/minimal back office for the catalog slice. It is *separate* from the public site — its own shell (`AdminShell`: sidebar + topbar), its own design tokens (`--admin-*` in `globals.css`), and it never touches `Header` / `Footer` / `LocaleProvider` styling.

- **Auth** — Firebase Authentication with session cookies, not NextAuth. `signInAdmin` posts email + password to the Identity Toolkit REST API from the server (the API key never reaches the browser), verifies the returned id token with `firebase-admin`, checks the email against the `ADMIN_EMAILS` allowlist, and only then issues an HttpOnly `admin_session` cookie. `src/lib/admin/session.ts` owns `getAdminSession()` (verify + allowlist), `createAdminSessionCookie()` and `clearAdminSessionCookie()`. `src/lib/firebase.ts` initialises the Firebase Admin app **lazily** so `next build` still succeeds without credentials.
- **Gates** — three of them, and all three must pass: `ADMIN_ENABLED=1` (deployment kill-switch), a valid Firebase session cookie, and an email on `ADMIN_EMAILS`. The env flag alone is *not* authorization; it only switches the surface off. Every admin server action calls `assertAdmin()` (env flag **and** session).
- **Routing** — Next 16 `src/proxy.ts` (the successor of `middleware.ts`, Node.js runtime) guards `/admin/:path*`. It only checks for the *presence* of the cookie; the cryptographic verification and the allowlist check happen server-side in `getAdminSession()`. The proxy deliberately never redirects `/admin/login` back to `/admin` — it cannot tell a valid cookie from a stale one, and doing so would loop; the login page performs that check itself. `ADMIN_ENABLED !== "1"` makes the proxy send every `/admin/*` request to `/`.
- **Route groups** — `src/app/admin/login/` is public; `src/app/admin/(secure)/` holds the guarded subtree. The guard lives in the `(secure)` layout behind a `<Suspense>` boundary (a `cookies()` read outside one is a build error under `cacheComponents`) and awaits `connection()` before verifying, because Firebase token verification reads the clock and `Date.now()` is not allowed while prerendering.
- **Routes** — `/admin` dashboard (counts per catalog table) and seven catalog tabs: `/admin/catalog/products`, `/packages`, `/service-types`, `/price-tiers`, `/places`, `/service-lines`, `/amenities`. Price tiers always show their **service-line scope** — labels repeat per line, so an operator must see which scope they are editing.
- **Transactions** — `/admin/transactions` (the index redirects to the first line) is the per-line booking back office: `transport`, `tour-package`, `fast-track`, `vip-service`, `evoa` (`TRANSACTION_LINES` in `src/lib/admin/transaction-lines.ts`). Four are real `ServiceLine` rows; **fast-track is a scoped view** of vip-service bookings whose items carry the fast-track `ServiceType`, not its own line. `setBookingStatus(id, next)` (`src/app/actions/admin-bookings.ts`) is the handover/cancel transition: `completed` only from `confirmed`, `cancelled` only from `awaiting_payment` or `confirmed`; `completed` / `cancelled` are **terminal** (any transition out of them is rejected with a friendly error). Cancelling a confirmed booking appends a `[CANCEL] Refund …` note computed from the cancellation policy. No stock write happens — terminal bookings stop counting, so handover/cancel releases the reserved units automatically (see Transport stock).
- **CRUD UX — create/update on full pages, delete in a modal.** Every catalog module follows the same three rules:
  - *Create* and *update* live on **dedicated pages**, never in a drawer or a modal: `/admin/catalog/<module>/new` and `/admin/catalog/<module>/[id]`. Both routes render the *same* component (`EntityFormPage`), so the edit page is the create page with prefilled values. The page has a "Kembali ke …" link, the field grid, and a footer with **Batal** (a plain link back to the list — cancelling never saves) and **Simpan** / **Simpan Perubahan**.
  - *Save* posts to the server action `saveAdminEntity({ table, id, values })` (`src/app/actions/admin-crud.ts`). It returns a **structured result** — `{ ok: true, message }` or `{ ok: false, error, field? }` — so a validation failure is rendered **on the field that caused it** instead of in a generic banner. On success a toast is shown and the browser returns to the list.
  - *Delete* opens the **"Confirm Delete"** modal (`DeleteConfirmModal`). It shows the record's exact name, warns that the action is irreversible, and asks the operator to retype the name in the field labelled *"Type the name to confirm deletion"* (placeholder *"Enter the exact name"*). **"Delete Permanently" stays disabled until the typed text matches the stored name byte for byte** — no trimming, no case folding. The server repeats the same comparison in `deleteAdminEntity()` before it deletes anything, and refuses with a friendly message when other rows still reference the record.
- **Server layer** — `src/app/actions/admin-crud.ts` is the form-shaped layer on top of `src/app/actions/admin.ts` (which keeps the `upsert*` business logic). It owns `saveAdminEntity`, `getAdminEntityName` and `deleteAdminEntity`, the friendly Indonesian messages, and the dependency checks. Deletes clean dependent rows explicitly (join rows such as `ProductAmenity` / `ProductAddOn`) instead of relying on cascade behaviour.
- **Components** (`src/components/admin/`) — `AdminShell`, `AdminSidebar`, `AdminTopbar`, `DataTable`, `Field`, `MoneyField`, `StatusToggle`, `EmptyState`, `EntityManager` (the shared table every tab plugs into: **Create** and **Edit** are `<Link>`s to the form pages, **Delete** opens the confirmation modal), `EntityFormPage` (the shared create/update page), `fields.tsx` (the field vocabulary: text / textarea / number / money / select / toggle / tags / multiselect), `DeleteConfirmModal` and `toast.tsx` (a module-level toast store plus `AdminToaster`, mounted in `AdminShell`, so a notification survives a client-side navigation). `AdminDrawer.tsx` was removed — create/edit no longer live in a drawer. `MoneyField` edits **raw integer USD cents** and previews the value as `$12.00` underneath, per the admin spec.
- **Field markup** — `Field` is a `<div>` wrapper with a `<label htmlFor>`; the control carries the id `field-<table>-<id|new>-<name>` so a label never points at the control of another (cached) page. The delete modal's input uses `useId()`.
- **Data access** — catalog lists load through server actions from client components (`listProducts`, `listPackages`, …), so the admin pages stay statically renderable and the database is never read during a prerender. Mutations are `upsert*` actions: an edit targets the row the operator picked **by `id`**, and the natural key (slug / label / code) must not already belong to a *different* row — creating a row with a taken natural key is rejected instead of silently overwriting it.
- **Route data** — the `[id]` pages read `params` **inside a `<Suspense>` boundary**; under `cacheComponents` a URL read outside a boundary triggers "Next.js encountered URL data during prerendering or a navigation".

**Customer accounts (`/login`, `/register`, `/account`):** the customer-facing counterpart of the admin area, sharing the same Firebase project but never the same session.

- **Roles** — the Postgres `User.role` column (`ADMIN` | `USER`) is the single source of truth. `ADMIN_EMAILS` is only a **bootstrap allowlist**: the first time an allowlisted email signs in at `/admin/login`, `ensureAdminAccount` promotes its row to `ADMIN`. After that the DB decides, so access is revoked by setting `role = 'USER'` on the row. `src/lib/accounts.ts` owns `syncAccount` (mirror a Firebase identity into the DB), `ensureAdminAccount` (admin bootstrap) and the role helpers.
- **Two sessions, never mixed** — `admin_session` (`src/lib/admin/session.ts`) and `user_session` (`src/lib/user/session.ts`), both HttpOnly Firebase session cookies. `getAdminSession()` requires the DB row to be `ADMIN`; `getUserSession()` **rejects** `ADMIN` rows. An admin therefore cannot browse as a customer, and a customer cannot reach `/admin`. The customer session TTL is 8 h by default, or 14 days when "Ingat saya" is checked.
- **Identity** — email + password goes through the Identity Toolkit REST API from the server (`src/lib/identity.ts`), so the API key never reaches the browser. Google sign-in uses the Firebase **Web** SDK popup in the browser (`src/lib/firebase-client.ts`, `NEXT_PUBLIC_FIREBASE_*` config) and hands the id token to the server, which verifies it before issuing the cookie. Password reset uses the Identity Toolkit `sendOobCode` endpoint and always answers the same way, so the form cannot be used to probe which addresses have accounts.
- **Registration rules** — a new account always starts as `USER`. An allowlisted (admin) email is refused with a message pointing at the admin area. If the DB write fails, the freshly created Firebase user is deleted again so the address is not left half-created.
- **Pages** — `/login` and `/register` use the **split-screen** `AuthShell` (`src/components/auth/`): a dark-blue brand panel on the left (hidden below `lg`), the form on a white canvas on the right. **These two pages deliberately render without `Header` / `Footer`.** `AuthField` renders the labelled inputs and the password eye toggle; `GoogleButton` renders the popup flow. The email input is **controlled** — React resets uncontrolled form fields after a form action completes, which would otherwise wipe the address on a failed attempt.
- **`/account`** — the signed-in customer's area: the hub plus `profile`, `orders` (and `orders/[code]/invoice`), `loyalty`, `payments`, `reviews`, `help` and `settings`. `AccountShell` (mounted in `src/app/account/layout.tsx`) wraps every one of them in the two-column frame — `AccountNav` on the left, the page on the right — so a panel is only its own content. The sidebar is `hidden lg:block`; below `lg` the hub at `/account` is the navigation. The printable invoice opts out of the frame.
- **Who is signed in** — `AccountProvider` (`src/components/providers/AccountProvider.tsx`) is mounted in the **root** layout and reads `getAccountOverview()` once per page load, after mount. `useAccountOverview()` returns `{ overview, loading, refresh }`; `UserMenu`, `AccountNav` and the account panels all read it instead of each calling the server again, and `refresh()` is for the forms that change the row (the profile editor). A guest simply gets `overview: null`. The session cookie is HttpOnly, so this client-side read is what keeps the public pages statically renderable.
- **Signing out** — `signOutUser()` deliberately does **not** redirect. `redirect("/")` is a client-side navigation, which leaves the already-mounted header holding its signed-in state; both callers (`UserMenu`, `SignOutButton`) therefore do `void signOutUser().then(() => window.location.assign("/"))` so the whole tree re-reads the session.
- **Session refresh** — `src/components/providers/SessionRefresh.tsx` keeps sessions alive with **sliding cookie renewal**: `UserSessionRefresh` (mounted in the root layout) and `AdminSessionRefresh` (mounted in `AdminShell`) re-issue the HttpOnly session cookie with its full TTL via `refreshUserSession` / `refreshAdminSession` — once on mount, every **30 minutes** while the tab is visible, and on `visibilitychange` when the last attempt is 30+ minutes old (laptops waking from sleep). A Google sign-in sends a fresh Firebase id token along; password-only sessions renew from the cookie alone. Failures are silent (the next interval retries) and the components render nothing.

### Bot protection — Cloudflare Turnstile

The customer password forms (`/login`, `/register`) are gated by a **Cloudflare Turnstile** widget. The Google sign-in popup is *not* gated (it never posts a form to the server).

- **Flow (canonical Turnstile)** — the browser renders the widget and produces a token; the token travels with the form; the **server** redeems it against `https://challenges.cloudflare.com/turnstile/v0/siteverify`. The secret key is never sent to the browser and siteverify is never called from the browser.
- **`src/lib/turnstile.ts`** (server-only) — `verifyTurnstileToken(token, expectedAction)` posts the token to siteverify and returns `true` only when the answer is `success: true`, the `action` matches the surface, and the `hostname` is in `TURNSTILE_HOSTNAMES` (an empty allowlist skips the hostname check and logs a warning). Every failure returns `false` and only a generic message reaches the browser.
- **`src/components/auth/TurnstileWidget.tsx`** (client) — renders the widget **explicitly** (`next/script` for `…/turnstile/v0/api.js` + `window.turnstile.render(...)`) into a `.cf-turnstile` container. The widget writes its token into the hidden `cf-turnstile-response` input, so the surrounding `useActionState` form submits it unchanged. Turnstile tokens are **single-use**, so the form bumps `resetSignal` whenever the server action returns an error and the widget calls `turnstile.reset()`.
- **Gated actions** — `signInUser` (action `login`) and `registerUser` (action `register`) in `src/app/actions/user-auth.ts` run the check **before** anything else; on failure they return `TURNSTILE_ERROR` ("Verifikasi keamanan gagal…"). The rest of each handler is unchanged — the widget only *gates* the flow.
- **Env** (`src/lib/turnstile.ts` reads them; documented in `env.example`) — `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (public), `TURNSTILE_SECRET` (server only, `.env` is gitignored), `TURNSTILE_HOSTNAMES` (comma-separated allowlist). The `action` string must match on both sides (`data-action` on the widget = the expected action server-side).
- **Before going live** — register the production domain on the Turnstile widget (Cloudflare's dashboard) *and* list it in `TURNSTILE_HOSTNAMES`; `localhost` must never appear in a production allowlist. The admin area (`/admin/login`) is not covered by the widget.
- **Local notes** — headless Chromium is flagged by Cloudflare and the widget stays on "Checking your Browser…" without a token; use a headed browser to test. The widget itself sets no CSP: the app sends no `Content-Security-Policy` header, and the `connect-src` policy seen in the console belongs to Cloudflare's own iframe.

**Settings as a config table:** `Setting` (key → JSON) holds what an operator should be able to change without a deploy — the taxes, the home popup, the hero copy, `booking.rules` and `vip.serviceInfo`. Two rules apply. First, `seedSettings()` in `scripts/seed-content.mts` **deletes every key it does not know about**, so a new key must be registered in `settingValues` (or `adminManagedSettingKeys`) or the next `npm run db:seed` wipes it. Second, `listTaxSettings()` scans *every* row and treats any **string** value ending in `%` or starting with `$` as a tax added to every booking — so a non-tax setting must be stored as a JSON **object**, never as such a string.

**Data flow:** copy, tabs, and SEO links still live in `src/data/home.ts`; service menus in `src/data/services.ts`; the search index in `src/data/search.ts`. Product/catalog data now comes from the database via `getCatalog` / `getProduct` actions, with the static data files acting as fallback. Components receive typed props (`CatalogDTO`, `ProductDetailDTO`, `BookingLookupResult`, …) imported from `@/types`. To change static fallback content, edit the data files; to change live catalog content, run the seeder (`npm run db:seed`) or use the reserved admin actions.

**Rendering boundary:** interactive widgets are `"use client"` — `Header`, `NavBar`, `HeroSearch`, `SectionBand`, `SeoLinkGrid`, `TabPills`, `Carousel`, `ServiceCatalog`, `BookingPanel`, `SearchResults`, `ProductDetail`, `BottomTabBar`, `StickyAppBanner`, `Footer` (reads i18n), `BannerStrip`, `SeoContent` (resolves bilingual DB copy in the active language), all four cards (`ProductCard`, `ArticleCard`, `DestinationCard`, `PromoCard`) and `PriceBlock`. Everything else (`Logo`, `Container`, `SectionHeading`, `ServiceLayout`, `icons.tsx`) is a server component. **Deliberate deviation from the original split:** `Footer`, `PriceBlock`, and the cards are client components because they read locale and format USD prices through `useLocale()` / `useMountedLocale()` — i18n and price formatting both live in the client-side locale context (there is no live-currency feature anymore; prices are always USD). Keep the remaining presentational components as server components.

**Cards:** `src/components/cards/` maps each data type to a card component using shared `Badge`, `PriceBlock`, `Rating`, and `Thumb` primitives. Images are intentional gradient placeholders: each data record carries a Tailwind `tone` string (e.g. `"from-sky-400 to-blue-600"`) rendered through `Thumb`, not real image assets. The SVGs in `public/` are unused create-next-app leftovers.

**Styling system:** design tokens are declared in `src/app/globals.css` under `@theme inline` (e.g. `--color-brand`, `--color-ink`, `--color-muted`, `--color-line`, `--color-canvas`, `--color-brand-soft`, `--color-danger`). Use the semantic utilities (`bg-brand`, `text-ink`, `border-line`, `bg-canvas`) rather than raw hex values. Font is Figtree via `next/font/google`, exposed as `--font-figtree` and mapped to `--font-sans`.

**Icons:** hand-rolled inline SVGs in `src/components/icons.tsx` driven by a `base()` prop helper (24×24, currentColor, 2px stroke). Add new icons there instead of importing an icon library.

**Conventions:** `@/*` aliases `src/*` (see `tsconfig.json`). Prices in the data layer and database are **integer USD cents**; at render time `useLocale().formatMoney(usdDollars)` formats them as USD (divide cents by 100 first) — there is no currency switching and no conversion at render time. The only USD→IDR conversion is the server-side Frankfurter charge rate frozen on the payment row at session creation (see Payments). Layout is mobile-first — fixed `BottomTabBar` (safe-area padded) on mobile, absolute-over-hero `Header` on desktop, and every section wraps content in `<Container>` (`mx-auto max-w-[1200px] px-4 sm:px-6`). The root layout sets `viewportFit: "cover"` so the bottom bar respects device safe areas.
